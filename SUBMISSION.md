## Архитектура и консистентность

Каждая метрика идентифицируется тройкой `(run_id, metric, step)`. Клиент
отправляет `batch_id`; пара `(run_id, batch_id)` уникальна, поэтому повторная
отправка batch безопасна и не создает повторное событие. Строки метрик также
имеют уникальный ключ, а при конфликте сохраняется первое значение.

Порядок доставки не считается порядком метрик. API возвращает каноническое
состояние, отсортированное по имени метрики и шагу.

Запись метрик и создание события выполняются в одной транзакции. ID события,
назначаемый базой данных, используется как SSE-курсор. После восстановления
соединения клиент отправляет `Last-Event-ID`, сервер возвращает пропущенные
durable-события, а UI повторно запрашивает полное состояние run. Поэтому
источником истины является база данных, а не накопленные UI-дельты.

## Изоляция проектов и silent failures

Каждое чтение run, добавление метрик, создание session и SSE-подписка сначала
проверяются по проекту, которому принадлежит API key или session. Доступ к
чужому проекту возвращает нормализованный `404`. ID run являются UUID, но
безопасность не зависит только от невозможности угадать ID.

API keys хранятся в виде хэшей. При ротации старые ключи отзываются. Session
cookie имеет флаги `HttpOnly` и `SameSite=Strict`.

Тесты проверяют:

- метрики, пришедшие в неправильном порядке;
- повторную отправку batch;
- позднюю метрику;
- восстановление SSE через `Last-Event-ID`;
- чтение, запись и SSE-доступ между проектами;
- неработоспособность старого ключа после ротации.

Транзакции откатываются при ошибке, поэтому частичная запись не возвращается
как успешная. Для медленных клиентов не создается бесконечная очередь:
клиент восстанавливается через durable replay. Для production дополнительно
нужны лимиты соединений, retention/compaction, redacted structured logs,
rate limiting и проверка timing side-channels.

## Результат тестов

Команда:

```text
python -m pytest -q
```

Результат:

```text
2 passed, 34 warnings in 1.14s
```

Тест консистентности подтверждает, что финальное состояние API совпадает с
каноническим состоянием в базе после описанных проблем доставки. Он не
проверяет ошибки браузерного рендеринга, race condition между несколькими
процессами, proxy buffering, поведение после удаления старых событий или
реальную перегрузку медленного клиента. Тест изоляции использует API и SSE,
но не заменяет полноценную browser automation проверку.

## Вердикт

**DON'T SHIP в текущем виде** для нагрузки 50 одновременных runs и 10
events/sec. SQLite WAL подходит для тестового задания, но не должен быть
production write/event path при такой нагрузке.

Первым изменением я бы перенес хранилище на PostgreSQL с outbox-таблицей,
добавил bounded SSE broker с replay-метриками и retention policy, затем
провел нагрузочный тест минимум на 500 events/sec с проверкой p95 latency и
отсутствия пропущенных event IDs.

## Использование AI и рефлексия

AI coding assistant использовался для черновой структуры FastAPI/SQLite и
первоначального набора тестов. Самостоятельно были проверены границы
транзакций, authorization paths, SSE replay, ротация ключей, Docker setup и
результаты тестов. После проверки была отдельно исправлена логика повторной
отправки batch и создания событий.

Больше всего меня удивило, насколько легко live UI может выглядеть корректно,
даже если одно событие потеряно. Поэтому безопаснее периодически получать
каноническое состояние из базы, чем бесконечно применять только дельты.
Основные оставшиеся риски — retention событий, backpressure,
наблюдаемость и multi-process deployment; поэтому итоговый вердикт —
не отправлять текущую реализацию в production без этих изменений.
